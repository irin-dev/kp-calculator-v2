# Скилл: КП-калькулятор v2

Инструкция предназначена для AI-разработчика, который сопровождает публичный репозиторий калькулятора коммерческих предложений. Она совместима с OpenCode, Claude Code, Cursor и другими инструментами, поддерживающими формат `SKILL.md`.

## Границы

- Skill объясняет сопровождение проекта, но не заменяет `README.md`, CI и пользовательскую документацию.
- Калькулятор имеет два пользовательских контура: разработка бота по квизу и витрина готовых продуктов.
- Репозиторий `kp-calculator-v2` — дипломная версия. Не добавляй в неё внутренние CRM, n8n, NocoDB, production-секреты или интеграции студии.
- Не меняй публичную историю и не делай push без явного разрешения владельца.
- Для обычного пользователя оставляй инструкции по кастомизации в `README.md`; если появится `docs/CUSTOMIZING.md`, ссылайся на него, но не создавай несуществующий файл.

## Требования и запуск

Требуется Python 3.10 или новее. Внешние пакеты для запуска не нужны.

Запускай из корня репозитория:

```text
python src/app.py
```

По умолчанию сервер доступен на `http://127.0.0.1:8000`. Порт можно изменить переменной окружения `PORT`.

Сервер:

- обслуживает статические файлы;
- отдаёт `data/quiz.json`;
- принимает ответы в `POST /api/estimate`;
- возвращает рассчитанный результат;
- не хранит реквизиты в коде.

## Единый источник правды

Числа и ветвление живут в двух местах:

- `data/quiz.json` — экраны, варианты ответов, переходы, веса, мягкие выходы и готовые продукты;
- `src/calculator.py` — формула, сбор параметров, вилка цены, скоринг и `evaluate`.

Фронтенд `src/static/main.js` не дублирует формулу. Он отправляет ответы в `POST /api/estimate` и показывает ответ сервера. `src/app.py` обслуживает HTTP-контур и конфигурацию отображения.

При изменении файлов соблюдай границу:

- вопросы, продукты, веса и переходы → `data/quiz.json`;
- формула и бизнес-правила → `src/calculator.py`;
- HTTP и конфигурация → `src/app.py`;
- состояние интерфейса и визуальный поток → `src/static/`;
- пользовательские тексты и схема запуска → `README.md`.

## Базовые проверки

Запускай из корня репозитория:

```text
python -m unittest discover -s tests -p "test_*.py" -v
python -m json.tool data/quiz.json
node --check src/static/main.js
git diff --check
```

Основной baseline — стандартный `unittest`; установка `pytest` не требуется. Если `pytest` уже установлен, дополнительно можно выполнить:

```text
python -m pytest tests/test_calculator.py -q
```

Текущий baseline покрывает 28 unit-тестов расчётной логики. После изменения тестов или числа сценариев обновляй это утверждение и документацию.

## Изменение воронки

1. Открой `data/quiz.json`.
2. Проверь блок `screens`: уникальные `id`, типы `single`/`multi`/`contact`, варианты, `weight`, `next` и `overrides`.
3. Проверь блок `weights`: базовые цены, интеграции, AI-модуль, админ-панель, локальный режим, срочность и границы вилки.
4. Проверь `soft_exits`, `ready` и правила перехода к консультации.
5. Не добавляй логику расчёта в JSON или JavaScript.
6. Добавь или обнови unit-тесты для нового перехода, веса или мягкого выхода.
7. Проверь серверный расчёт и ручные сценарии: сценарный бот, AI-бот, гибрид, готовый продукт, мягкий выход и созвон.
8. Обнови README, если изменились пользовательские сценарии или структура данных.

## Изменение формулы

1. Меняй расчёт только в `src/calculator.py`.
2. Сохрани входные ключи `answers` совместимыми с `src/static/main.js`.
3. Добавь тесты для новой формулы, границ и скоринга.
4. Проверь, что `evaluate()` возвращает согласованный результат для `POST /api/estimate`.
5. Обнови описание формулы в `README.md`, если изменилась пользовательская логика.

## Работа с конфигурацией и данными

- Шапка КП получает реквизиты из `.env` или переменных окружения.
- `.env` нельзя коммитить; используй `.env.example` как шаблон.
- Не помещай реальные телефоны, email, ИНН, токены, webhook и внутренние адреса в skill, README, JSON или код.
- Для локальной проверки можно использовать вымышленные значения или оставить переменные пустыми.
- Если lead-flow подключается в отдельной боевой версии, держи endpoint настраиваемым и не считай дипломный репозиторий местом для production-конфигурации.

## Проверка перед завершением изменения

Перед завершением работы обязательно проверь:

```text
git status --short
python -m unittest discover -s tests -p "test_*.py" -v
python -m json.tool data/quiz.json
node --check src/static/main.js
git diff --check
```

Перед коммитом:

- просмотри `git diff` целиком;
- убедись, что в индекс попадают только намеренные файлы;
- не добавляй чужие незакоммиченные изменения;
- не включай `.env`, секреты, ПДн и внутренние интеграции;
- укажи в commit-сообщении, что менялся skill, а не код калькулятора;
- push выполняй только после отдельного разрешения владельца.

## Релизная дисциплина

Дипломную версию можно считать готовой к защите только после проверки:

- чистого `git status` для релизной копии;
- всех unit-тестов;
- валидного `data/quiz.json`;
- валидного `src/static/main.js`;
- запуска из чистого checkout;
- фиксации commit SHA или тега в release.

Production-версия студии должна собираться из отдельного commit или тега, иметь собственную историю и не получать изменения из дипломного репозитория автоматически.
