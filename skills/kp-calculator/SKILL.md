# Скилл: КП-калькулятор v2

Инструкция для AI-ассистента, который сопровождает публичный репозиторий калькулятора
коммерческих предложений. Формат `SKILL.md` поддерживают Claude Code, OpenCode и Cursor.

## Как подключить скилл

Имя каталога должно совпадать с `name` во frontmatter — иначе ассистент его не увидит.

| Инструмент | Куда положить (в этом репозитории) | Куда положить (личный, во всех проектах) |
|------------|--------------------------------------|--------------------------------------------|
| Claude Code | `.claude/skills/kp-calculator/SKILL.md` | `~/.claude/skills/kp-calculator/SKILL.md` |
| OpenCode | `.opencode/skills/kp-calculator/SKILL.md` | `~/.config/opencode/skills/kp-calculator/SKILL.md` |
| Cursor | `.cursor/skills/kp-calculator/SKILL.md` | — |

Файл лежит в репозитории по пути `skills/kp-calculator/SKILL.md`. Чтобы установить,
скопируй каталог целиком: править пути внутри не нужно.

## Границы

- Скилл описывает сопровождение проекта, но не заменяет `README.md`, CI и пользовательскую
  документацию. Инструкции для обычного пользователя оставляй в `README.md`.
- У калькулятора два пользовательских контура: разработка бота по квизу и витрина
  готовых продуктов. Не смешивай их.
- Это дипломная версия, отдельная от рабочей. Не добавляй сюда внутренние системы,
  секреты, боевые интеграции и реальные прайсы.
- Не меняй публичную историю и не делай push без явного разрешения владельца.
- Не создавай несуществующие файлы: если появится `docs/CUSTOMIZING.md`, ссылайся на него,
  но не придумывай путь.

## Требования и запуск

Python 3.10 или новее. Внешние пакеты не нужны — только стандартная библиотека.

Запускай из корня репозитория:

```text
python src/app.py
```

Сервер слушает `http://127.0.0.1:8000`. Порт меняется переменной окружения `PORT`
(например, `PORT=8801 python src/app.py`) — полезно, если порт уже занят.

### Реальные маршруты

| Метод | Путь | Ответ |
|--------|------|-------|
| GET | `/` | интерфейс калькулятора |
| GET | `/data/quiz.json` | экраны, веса, продукты — тот же файл, что лежит в репозитории |
| GET | `/config.json` | шапка КП, собирается из `.env` |
| GET | `/data/config.json` | синоним `/config.json`, тот же ответ |
| POST | `/api/estimate` | расчёт по ответам |

Других маршрутов нет: `/api/quiz` вернёт 404, это не ошибка развёртывания.

## HTTP-контракт `POST /api/estimate`

Тело запроса — **плоский JSON-объект**, без обёртки. Ключи — идентификаторы экранов
из `data/quiz.json`, значения — строки или списки строк.

Неправильно (вернёт `price: null` и `branch: "unknown"`):

```json
{ "answers": { "budget": "mid_30_100" } }
```

Правильно:

```json
{
  "purpose": "sell",
  "budget": "mid_30_100",
  "platform": ["tg", "wa"],
  "brain": "scripted",
  "capabilities": ["faq", "booking"],
  "integrations": ["crm"],
  "deadline": "no_rush",
  "decision": "self"
}
```

Ответ всегда содержит семь полей:

| Поле | Содержимое |
|------|-----------|
| `branch` | `scripted`, `ai`, `hybrid` или `unknown` |
| `soft_exit` | метка раннего выхода или `null` |
| `consult` | `{needed, reasons[]}` — нужна ли консультация и почему |
| `price` | расчёт вилки или `null` (см. ниже) |
| `terms` | сроки или `null` |
| `included` | список того, что входит в КП |
| `score` | `{heat, branch, budget_fork}` — квалификация лида |

`price` при наличии цены: `{estimate, min, max, base, platform_mult, adders, ai_module, scale}`.

Проверенные ответы для приведённого запроса:

```json
{
  "branch": "scripted",
  "consult": { "needed": false, "reasons": [] },
  "price": {
    "estimate": 39000, "min": 35000, "max": 49000,
    "base": 25000, "platform_mult": 1.25,
    "adders": 8000.0, "ai_module": 0, "scale": 1.0
  },
  "terms": "2-3 недели",
  "score": { "heat": "warm", "branch": "scripted", "budget_fork": "30-100к" }
}
```

Самопроверка без сервера — запусти модуль напрямую:

```text
python src/calculator.py
```

## Норма или ошибка

Эти ответы **штатные**, чинить их не нужно:

- `price: null` и `terms: null` при `branch: "hybrid"` или `branch: "unknown"`.
  Точную цену для гибрида не считают by design — заявка уходит на созвон
  (`src/calculator.py`, функция `estimate_range`).
- `branch: "unknown"` при пустом или неполном теле запроса: значит, ключи не совпали
  с идентификаторами экранов.
- `consult.needed: true` с непустым `reasons` — это подсказка менеджеру, а не сбой.
- Пустые строки в `config.json`, если `.env` не заполнен, — штатно.
- Ответ `400` с `{"error": "..."}` — расчёт остановлен из-за расхождения `quiz.json`
  и `src/calculator.py` (например, вес не классифицирован). Это ошибка развёртывания,
  не пользователя: подробности в логе сервера (`calc config error:`), клиенту
  показывается внятный текст без трейсбека. Проверь `validate_weights()` и
  `python src/calculator.py` локально.

## Единый источник правды

Числа и ветвление живут в двух местах:

- `data/quiz.json` — экраны, варианты, веса, переходы, мягкие выходы, готовые продукты;
- `src/calculator.py` — формула, вилка цены, скоринг, `evaluate()`.

`src/static/main.js` формулу не дублирует: он отправляет ответы в `POST /api/estimate`
и показывает ответ сервера. Добавлять расчёты в JavaScript или в JSON запрещено.

Кто что читает из `quiz.json`:

| Ключ | Читает |
|------|--------|
| `screens`, `weights`, `rules`, `soft_exits` | `src/calculator.py` |
| `ready`, `intro`, `consult`, `pd` | `src/static/main.js` |
| `version` | служебный, правок не требует |

Граница изменений:

- вопросы, продукты, веса, переходы → `data/quiz.json`;
- формула и бизнес-правила → `src/calculator.py`;
- HTTP и конфигурация → `src/app.py`;
- состояние интерфейса и визуальный поток → `src/static/`;
- пользовательские тексты и схема запуска → `README.md`;
- лицензия → `src/make-license.py` (генерирует `LICENSE` из `.env`).

## Новая услуга или интеграция: обязательный порядок

`weight` в `quiz.json` — это ссылка на вес, а не сам вес. Пока код не знает, в какую
категорию положить число, оно молча выбрасывалось из счёта. Сейчас это ошибка
вместо тишины, но порядок действий всё равно обязательный:

1. Объявить вес в `data/quiz.json` → `weights`.
2. Навесить его на опцию экрана → `{"value": "erp", "weight": "integration_erp"}`.
3. Классифицировать вес в `src/calculator.py` — **Шаг 0, карта весов**.
4. Добавить тест на эту услугу в `tests/test_calculator.py`.
5. Прогнать `python -m unittest discover -s tests -p "test_*.py" -v`.

Пропуск шага 3 даёт `ValueError` в `collect_parameters` — счёт не покажется вовсе.
Это лучше, чем заниженная смета, но пользователь её не увидит, поэтому шаг обязателен.

| Вес в `quiz.json` | Константа в коде | Куда попадает |
|-------------------|------------------|---------------|
| `integration_crm`, `integration_payments`, `integration_sheets` | `INTEGRATION_WEIGHTS` | `params.integrations` → `price.adders` |
| `ai_knowledge`, `ai_finetune` | `AI_MODULE_WEIGHTS` | `params.ai_module` |
| `admin_panel` | `FLAG_WEIGHTS` | `params.admin_panel` → `price.adders` (сумма берётся из таблицы) |
| `local_multiplier`, `urgency_multiplier` | `MULTIPLIER_WEIGHTS` | множитель `price.scale` |

Согласованность проверяется автоматически:

- `validate_weights(quiz)` — веса, которые есть в таблице, но не классифицированы в коде;
- `undefined_weights(quiz)` — веса, на которые ссылаются опции, но которых нет в `weights`;
- `python src/calculator.py` печатает оба списка. Непустой вывод = конфиг разошёлся с кодом.

Отдельно про множители: добавления в `MULTIPLIER_WEIGHTS` **недостаточно** — новый
множитель надо ещё встроить в формулу в `estimate_range`, иначе он будет учтён как
известный, но не повлияет на цену. Для денежных весов достаточно шагов 1–4.


## Базовые проверки

Запускай из корня репозитория:

```text
python -m unittest discover -s tests -p "test_*.py" -v
python -m json.tool data/quiz.json
node --check src/static/main.js
git diff --check
```

Первый baseline — стандартный `unittest`, установка `pytest` не нужна. Если `pytest`
уже установлен, можно дополнительно выполнить `python -m pytest tests/test_calculator.py -q`.

Текущий baseline — 33 unit-теста расчётной логики (из них 5 на согласованность
таблицы весов и кода). После изменения тестов или числа сценариев обнови это
утверждение здесь и в `README.md`.

## Изменение воронки

1. Открой `data/quiz.json`.
2. Проверь блок `screens`: уникальные `id`, типы `single` / `multi` / `contact`,
   варианты в `options`, `weight` у опций и `next` у экрана.
3. Проверь блок `weights`: базовые цены, интеграции, AI-модуль, админ-панель,
   локальный режим, срочность и границы вилки. В публичной версии значения учебные —
   не подставляй реальный прайс.
4. Проверь `soft_exits`, `ready` и правила перехода к консультации.
5. Учитывай, что поле `overrides` в `quiz.json` сейчас **ничем не читается**: код его
   игнорирует. Не рассчитывай на него и не описывай его как рабочую механику.
6. Не добавляй логику расчёта в JSON или JavaScript.
7. Добавь или обнови unit-тесты для нового перехода, веса или мягкого выхода.
8. Проверь серверный расчёт и ручные сценарии: сценарный бот, AI-бот, гибрид,
   готовый продукт, мягкий выход и созвон.
9. Обнови `README.md`, если изменились пользовательские сценарии или структура данных.

## Изменение формулы

1. Меняй расчёт только в `src/calculator.py`.
2. Сохрани входные ключи `answers` совместимыми с `src/static/main.js`.
3. Добавь тесты для новой формулы, границ и скоринга.
4. Проверь, что `evaluate()` возвращает согласованный результат для `POST /api/estimate`.
5. Обнови описание формулы в `README.md`, если изменилась пользовательская логика.

## Конфигурация, данные, лицензия

- Шапка КП берётся из `.env` или переменных окружения. `.env` не коммитится,
  `.env.example` — шаблон.
- Имя правообладателя для лицензии лежит в `.env` как `LICENSE_HOLDER` и не
  подставляется в КП. После заполнения выполни `python src/make-license.py` —
  файл `LICENSE` создастся сам. Пока переменная пуста, скрипт завершится с кодом 2
  и лицензию не создаст: подставлять выдуманное имя нельзя.
- Не помещай реальные телефоны, email, ИНН, токены, webhook и внутренние адреса
  в скилл, `README.md`, JSON или код.
- Для локальной проверки используй вымышленные значения или оставляй переменные пустыми.
- Если lead-flow подключается в отдельной боевой версии, держи endpoint настраиваемым
  и не считай дипломный репозиторий местом для production-конфигурации.

## Проверка перед завершением изменения

Перед тем как закончить работу, выполни:

```text
git status --short
python -m unittest discover -s tests -p "test_*.py" -v
python -m json.tool data/quiz.json
node --check src/static/main.js
git diff --check
```

Ожидаемо: 33 теста, ноль ошибок, `json.tool` и `node --check` без вывода.

Перед коммитом:

- просмотри `git diff` целиком;
- убедись, что в индекс попадают только намеренные файлы;
- не добавляй чужие незакоммиченные изменения;
- не включай `.env`, секреты, ПДн и внутренние интеграции;
- укажи в сообщении коммита, что менялся скилл, а не код калькулятора;
- push выполняй только после отдельного разрешения владельца.

## Релизная дисциплина

Дипломную версию можно считать готовой к защите только после проверки:

- чистого `git status` в релизной копии;
- всех unit-тестов;
- валидного `data/quiz.json`;
- валидного `src/static/main.js`;
- запуска из чистого checkout;
- созданного `LICENSE`;
- фиксации commit SHA или тега в release.

Production-версия студии собирается из отдельного коммита или тега, имеет собственную
историю и не получает изменения из дипломного репозитория автоматически.
